# i18n — internationalization and timezone-aware rendering

**Status:** design

**Date:** 2026-05-19

**Branch:** `feat/i18n`

## Goals

1. Ship the todo-app in **English, Spanish, French, and German** with a clean
   path to add more (including languages with complex plural rules) later.
2. Render every datetime in the user's **locale and timezone**, server-side,
   so the page is correct on first paint without a layout shift.
3. Avoid introducing a JavaScript build pipeline.
4. Bundle two adjacent improvements that the i18n work either uncovers or
   prerequisites: **CSP nonces** (replacing the static-CSP layer so we can
   keep one tiny inline script for the datetime upgrader) and
   **`Cache-Control: private, no-cache` on HTML responses** (closes a
   pre-existing safety gap that becomes more interesting once the app sits
   behind a CDN). Also fold in **content-hashed static asset URLs** with
   long-lived caching so we don't lose that thread.

## Non-goals (v1)

- Relative time ("3 minutes ago"). Out of scope; `Intl.RelativeTimeFormat`
  is a small client-side follow-up.
- Slavic / Arabic plurals. The Fluent path supports them; we just won't ship
  translations for them in v1.
- Currency, numbers, RTL languages.
- Per-locale URL prefixes (`/es/`, `/fr/`). The cookie/profile path is
  enough for a private app; URL prefixes can be introduced later for any
  future public marketing surface without retrofitting the authenticated
  app.
- Authenticated timezone settings page. Cookie-based delivery + a
  `users.timezone` column written by future settings UI is enough for v1.
- FTL autoreload in dev. The podman-FS-events issue documented in
  `CLAUDE.md` would need polling here too; accept a server restart on
  translation edits for v1.

## Architecture

### Crate layout

A new `crates/i18n/` crate, mirroring how `observability` is split out.
Public surface:

- `Locales` — owns loaded Fluent bundles; has `Static` and `Reloading`
  variants paralleling `Templates`.
- `negotiate(accept_lang: Option<&str>, cookie: Option<&str>, profile: Option<&str>) -> LanguageIdentifier`
  — applies the precedence rules below.
- `Tz` newtype around `time_tz::Tz` for handler use.
- Two `minijinja` helpers, registered when an `Environment` is built:
  - `t(id, **kwargs) -> String` — message lookup.
  - `datetime(value, style="medium") -> String` — produces the full
    `<time datetime="…">…</time>` element.

Dependency edges: `app → i18n → (fluent, fluent-templates, fluent-langneg,
time-tz, icu_datetime, icu_calendar, icu_locid, minijinja)`. No new
edges from `domain` or `storage`.

ICU note: `icu_datetime` ships CLDR data either as a baked-in provider
(`icu_provider_baked`, ~1–2 MB added to the binary depending on which
locales are compiled in) or via a blob loaded at runtime
(`icu_provider_blob`). For v1, **bake in only the four supported locales**
to keep the cost bounded. If we add a locale later, we recompile the
provider data — a one-line change to the codegen step.

### Domain + storage

`crates/domain`:

```rust
pub struct User {
    pub id: UserId,
    pub email: String,
    pub password_hash: String,
    pub created_at: OffsetDateTime,
    pub locale: Option<String>,    // new
    pub timezone: Option<String>,  // new
}
```

Both nullable; validation lives at the HTTP edge against the supported
sets — domain stays I/O-free.

`crates/storage`:

- Migration `migrations/0003_user_i18n_prefs.sql`:

  ```sql
  ALTER TABLE users ADD COLUMN locale   TEXT NULL;
  ALTER TABLE users ADD COLUMN timezone TEXT NULL;
  ```

- `UserRepository::update_preferences(user_id, locale, timezone)`.

### Request context

A middleware layer in `crates/app/src/middleware/i18n.rs` populates two
request extensions on every request:

- `RequestLocale(LanguageIdentifier)`
- `RequestTz(time_tz::Tz)`

Handlers read them via `Extension<RequestLocale>` / `Extension<RequestTz>`
and add them to the template context. The `t()` and `datetime()` template
helpers read the same values from the context (passed as `_locale` and
`_tz` context keys to avoid stringly-typed misuse).

## Locale negotiation

Precedence per request:

1. Authenticated user's `users.locale` if non-NULL and in the supported set.
2. Non-signed `locale` cookie (set by the language switcher).
3. `Accept-Language` header negotiated via
   `fluent_langneg::negotiate_languages` against the supported set.
4. `"en"` fallback.

Supported set: `const SUPPORTED: &[&str] = &["en", "es", "fr", "de"]`.

Output is also written to `<html lang="…">` so the client-side date
upgrader uses it directly.

## Message catalogs (Fluent)

Layout:

```
locales/
  en/{main,auth,todos}.ftl
  es/{main,auth,todos}.ftl
  fr/{main,auth,todos}.ftl
  de/{main,auth,todos}.ftl
```

Loaded via `fluent_templates::ArcLoader::builder("locales", langid!("en"))`
once at startup. Fluent's built-in fallback chain handles missing keys:
locale → en → render the ID literal + log a warning.

Template usage:

```
{{ t("signup-heading") }}
{{ t("todo-count", count=todos|length) }}
```

`fluent-templates` doesn't ship a `minijinja` integration; we wire one in
`crates/i18n` (~30 lines): a `t` closure registered as a global function
that reads `_locale` from the template context and calls into the
`fluent-templates` `Loader` for the message lookup.

## Validation error localization

`validator` attribute messages hold Fluent **IDs**, not English text:

```rust
#[validate(email(message = "validation-email-invalid"))]
pub email: String,
```

The HTTP error mapper in `crates/app/src/error.rs` walks the
`ValidationErrors`, pulls each `message` (`Option<Cow<'static, str>>` in
`validator` 0.18), and resolves through `t()` using the request locale.
Domain stays oblivious.

## Timezone delivery

- Cookie `tz` (non-signed, `Path=/`, `Max-Age=31536000`, `SameSite=Lax`)
  carries an IANA tz id.
- Server precedence: authenticated `users.timezone` → cookie → `UTC`
  fallback.
- Cookie value is validated server-side via
  `time_tz::timezones::find_by_name`; unknown values are dropped to UTC
  and increment `i18n_invalid_tz_total`.

## Datetime rendering (server + client)

Server-side baseline — the `datetime` minijinja helper emits:

```html
<time datetime="2026-05-19T13:00:00Z" data-style="medium">
  19 May 2026, 13:00 UTC
</time>
```

- `datetime` attribute is always the original UTC `OffsetDateTime` in
  ISO-8601 — the canonical source of truth.
- Inner text is a best-effort render: convert UTC → user's tz via
  `time-tz`, then format using `icu_datetime` for locale-correct CLDR
  patterns ("May 19, 2026, 1:00 PM" / "19 may 2026, 13:00" / "19 mai
  2026 à 13:00" / "19. Mai 2026, 13:00"). `fluent-bundle`'s own
  `DATETIME()` builtin is a near-passthrough and **not** used for this;
  we go direct to ICU so the server-rendered text matches what the
  client-side `Intl.DateTimeFormat` will produce. This is what no-JS
  clients and search engines see.
- `data-style` is one of `short` | `medium` | `long` and maps directly to
  `Intl.DateTimeFormat`'s `dateStyle` option.

Inline upgrader in `<head>` of `base.html`, executes synchronously before
body parsing so there is no FOUC:

```html
<script nonce="{{ csp_nonce }}">
  (() => {
    const tz = Intl.DateTimeFormat().resolvedOptions().timeZone;
    if (!document.cookie.split('; ').some(c => c.startsWith('tz='))) {
      document.cookie = `tz=${tz}; path=/; max-age=31536000; samesite=lax`;
    }
    const locale = document.documentElement.lang || "en";
    const upgrade = (root) => {
      for (const el of root.querySelectorAll("time[datetime]")) {
        const style = el.dataset.style || "medium";
        const fmt = new Intl.DateTimeFormat(locale, {
          dateStyle: style, timeStyle: "short", timeZone: tz
        });
        el.textContent = fmt.format(new Date(el.dateTime));
      }
    };
    upgrade(document);
    document.body.addEventListener("htmx:after:swap", e => upgrade(e.target));
  })();
</script>
```

The htmx event listener ensures `<time>` elements inserted by fragment
swaps get upgraded too.

## Language switcher

Header dropdown, htmx-driven:

```html
<form hx-post="/preferences/locale"
      hx-trigger="change from:find select"
      hx-swap="none">
  <select name="locale" aria-label="{{ t('language-switcher-label') }}">
    <option value="en">English</option>
    <option value="es">Español</option>
    <option value="fr">Français</option>
    <option value="de">Deutsch</option>
  </select>
</form>
```

`POST /preferences/locale`:

- Validates the value against the supported set.
- Sets `Set-Cookie: locale=<value>; Path=/; Max-Age=31536000; SameSite=Lax`.
- If authenticated, persists to `users.locale`.
- Returns `HX-Refresh: true` so htmx triggers a full reload in the new
  locale (every visible string changes — full reload is correct here, not
  a partial swap).
- Rate-limited per-IP like the auth routes.

## Security middleware updates (bundled)

### CSP nonces

Replace the static `SetResponseHeaderLayer` for `Content-Security-Policy`
in `crates/app/src/middleware/security.rs` with a `from_fn` middleware
that:

1. Generates a 128-bit nonce per request, base64-encoded.
2. Inserts `CspNonce(value)` on request extensions.
3. After the handler runs, writes
   `script-src 'self' 'unsafe-eval' 'nonce-<value>'` into the response CSP.

Templates receive the nonce as a standard context key `csp_nonce`,
populated by handlers alongside `user`. The datetime upgrader and any
future inline `<script>` use it via `nonce="{{ csp_nonce }}"`.

`'unsafe-eval'` stays because Alpine.js and htmx 4's `hx-on::*` attributes
both runtime-compile expressions. That's an orthogonal axis to
`'unsafe-inline'`.

All other security headers (`X-Content-Type-Options`, `Referrer-Policy`,
HSTS, `Permissions-Policy`) remain as static `SetResponseHeaderLayer`s.

### Cache-Control default

A `SetResponseHeaderLayer::if_not_present` layer sets:

```
Cache-Control: private, no-cache
```

on every response by default. Handlers and the static-asset path can
override (see asset hashing below). This closes the pre-existing safety
gap where a shared cache could store cookied HTML, and prevents i18n
cross-locale contamination at any CDN that lands in front of the app
later.

## Asset hashing and long-lived caching (bundled)

The vendored JS files (`htmx-4.0.0-beta3.min.js`,
`alpine-3.15.12.min.js`, etc.) are already version-stamped in their
filenames. `static/css/app.css` is not — Tailwind rewrites it in place.

### Manifest

At startup, an `Assets` value walks `static/` and builds an in-memory
manifest. For each file:

- Compute `sha256(content)`, take the first 8 hex chars as the hash.
- Manifest entry: `"css/app.css" → "css/app.<hash>.css"`.

A minijinja global `asset(logical_path) -> String` does the lookup. In
production, it returns the hashed URL; in dev it returns the raw path
(so Tailwind `--watch` can edit `app.css` freely without server
restarts).

### Request handling

A small custom handler ahead of the existing `ServeDir` recognizes the
hashed URL pattern `<dir>/<name>.<8hex>.<ext>`:

- If the unhashed file exists at `<dir>/<name>.<ext>` and the manifest
  hash matches: serve it with
  `Cache-Control: public, max-age=31536000, immutable`.
- Otherwise (hash mismatch or file missing): 404.

Unhashed URLs continue to be served by `ServeDir` as today, with
`Cache-Control: public, max-age=300` (short, so a forgotten
`asset()` call still rolls out within minutes). Precompressed
gzip/brotli siblings continue to be served via
`precompressed_gzip().precompressed_br()`.

### Template migration

`templates/base.html` updates:

```html
<link rel="stylesheet" href="{{ asset('css/app.css') }}">
...
<script src="{{ asset('vendor/htmx-4.0.0-beta3.min.js') }}" defer></script>
<script src="{{ asset('vendor/htmx-4.0.0-beta3-ext-alpine-compat.js') }}" defer></script>
<script src="{{ asset('vendor/alpine-3.15.12.min.js') }}" defer></script>
```

The vendored JS already includes a version stamp; the manifest hash is
appended *on top* of that. Net URL: `vendor/htmx-4.0.0-beta3.min.<hash>.js`.
Verbose but correct, and consistent with `app.css`.

### Dev vs prod

`Assets::dev()` returns raw paths and sets `Cache-Control: no-cache` on
the static layer. `Assets::production()` builds the manifest once at
startup. Selected by the same `APP__TEMPLATE_AUTORELOAD` config flag that
already selects `Templates::dev` vs `Templates::production` — same axis,
same toggle, no new knob.

## Fallbacks and missing-key behavior

- Missing message in target locale → Fluent's chain resolves to English.
  If English is also missing, render the ID literal and log a warning
  with the locale and key.
- Missing variable in a message → Fluent renders `{$varname}` literal
  and logs.
- Invalid locale in cookie/profile → fall through to the next precedence
  step.
- Invalid tz in cookie → drop to UTC and increment
  `i18n_invalid_tz_total`.

## Observability

New metrics (cardinality bounded):

- `i18n_locale_total{locale}` — per-request counter (cardinality 4).
- `i18n_missing_key_total{locale, key}` — bounded by message IDs (low
  hundreds).
- `i18n_invalid_tz_total` — counter.

Span fields:

- `request.locale`
- `request.tz`

Both added to the request span (which already exists via `TraceLayer`).

## Testing

Unit tests (`crates/i18n/tests/`):

- `negotiate.rs` — precedence rules: profile > cookie > Accept-Language
  > default; unsupported values fall through.
- `tz_validate.rs` — accepts valid IANA names, rejects invalid.
- `keys.rs` — greps the workspace for `t("…")` calls, asserts every
  referenced ID exists in `locales/en/`. Run as a `cargo test`.

Integration tests (`crates/app/tests/`, using the existing
testcontainers harness):

- `i18n_flow.rs`:
  - `Accept-Language: es` returns Spanish HTML.
  - Setting the `locale` cookie via the switcher persists across
    requests.
  - Authenticated user with `users.locale = 'fr'` always sees French
    regardless of cookie/header.
- `i18n_datetime.rs`:
  - `<time datetime="…">` attribute is always UTC.
  - Inner text uses the right server-side format for the locale.
  - `tz` cookie shifts the inner text accordingly.
- `csp_nonce.rs`:
  - Two requests get different nonces.
  - The CSP header contains exactly the nonce embedded in the page.
- `asset_hash.rs`:
  - `asset('css/app.css')` returns a hashed URL in production mode.
  - The hashed URL returns the same bytes as the unhashed one, with
    `Cache-Control: public, max-age=31536000, immutable`.
  - A hash mismatch returns 404.
- `cache_control.rs`:
  - HTML responses carry `Cache-Control: private, no-cache`.
  - Hashed static assets carry the immutable header.

## Open questions / future work

- **Static asset hashing for templates and FTL files** — not needed; both
  are server-internal.
- **Relative time** — add `Intl.RelativeTimeFormat` upgrade in a follow-up.
- **Authenticated settings page** — exposes the tz/locale profile fields
  via a UI; cookie path is sufficient for v1.
- **FTL hot-reload in dev** — polling-based watcher, mirroring the
  Tailwind v4 poll loop. Defer until the lack becomes painful.
- **CDN-ready static assets** — content hashing lands here, but if we
  ever switch from in-tree static serving to S3/Cloudflare R2, the
  manifest would migrate to a `manifest.json` shipped with the deploy.
